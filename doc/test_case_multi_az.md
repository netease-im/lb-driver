# 多可用区（AZ）测试用例

本文覆盖 AZ 识别、亲和下发、故障兜底、恢复回切、动态配置和兼容性。所有用例初始状态均为「未执行」，不根据已有日志或其他测试结果标记通过。

## 测试准备

* 使用独立测试环境，配置 `proxy.policy=az`，准备 az1、az2 两个互不重叠的 IPv4 网段。
* 准备三个 sql-proxy：P1 属于 az1，P2 属于 az2，P3 仅在默认集合中；默认 `proxy` 为 `[P1, P2, P3]`。测试本 AZ 多节点时，额外增加 P2b 到 az2。
* 分别准备 az1、az2 和不匹配任何 AZ 网段的业务节点；除显式覆盖用例外，URL 不配置 `az`、`ip`，验证自动识别。
* 以下均为虚构示例地址，执行时替换为测试环境地址；文中的 P1、P2、P3 分别对应这三个代理：

| 角色 | 测试地址 | 预期归属 |
| --- | --- | --- |
| az1 业务网段 | `192.0.2.0/25` | az1 |
| az2 业务节点 | `192.0.2.130`、`192.0.2.131` | az2（网段为 `192.0.2.128/25`） |
| 未匹配业务节点 | `203.0.113.10` | 默认集合 |
| P1 | `198.51.100.11:2883` | az1 |
| P2 | `198.51.100.12:2883` | az2 |
| P3 | `198.51.100.13:2883` | 仅默认集合 |

* 开启 driver 的 `logStats=true`，记录 config-server 的 `stats.log`，关注 `clientFeatureLevel`、`clientVersion`、`policy.applied`、`az.applied` 和响应集合。
* 准备持续 SQL 流量，包括查询、写入和事务；记录成功率、异常、耗时，以及故障注入、首次失败、首次恢复、回切和连接补齐的时间。写入使用独立测试表与可核对的唯一标识。
* 记录实际 `connectTimeout`、`socketTimeout`、`recoverCheckCount`、`azRefreshIntervalSeconds`、健康检查及连接均衡周期。超时和恢复时长按实际配置评估，不把后台连接补齐耗时直接当成业务中断时长。
* 每个故障用例结束后恢复代理、网络和配置，确认连接池稳定后再执行下一项。涉及 Druid 时按版本要求配置 `LbdDruidFilter`。

## AZ 识别与集合下发

| 编号 | 用例与操作 | 预期结果 | 测试结果 |
| --- | --- | --- | --- |
| AZ-01 | az1 节点使用不带 `az`、`ip` 的 URL 启动并持续执行 SQL | driver 自动上报本机 IP；服务端识别 az1，返回 `policy=az` 和 `[P1]`；稳定后仅使用 P1，SQL 正常 | 未执行 |
| AZ-02 | az2 节点使用不带 `az`、`ip` 的 URL 启动并持续执行 SQL | 服务端识别 az2，下发 `[P2]`；稳定后仅使用 P2，SQL 正常 | 未执行 |
| AZ-03 | 未匹配任何 AZ 网段的节点启动 | 返回 `policy=default` 和 `[P1, P2, P3]`；连接在可用代理间逐步均衡，不进入 AZ fallback | 未执行 |
| AZ-04 | az2 节点显式配置 `az=az1`，同时上报 az2 的 IP | 显式 AZ 优先，返回 `[P1]`，不按 IP 选择 P2 | 未执行 |
| AZ-05 | 请求传入不存在的 `az`，同时携带可匹配 az2 的 `ip` | 无效 AZ 不阻断后续匹配，按 IP 返回 `[P2]` | 未执行 |
| AZ-06 | URL 显式设置 az1 的 `ip`，请求来源属于 az2；不传 `az` | 请求参数 IP 优先于来源 IP，返回 `[P1]` | 未执行 |
| AZ-07 | 请求不携带 `az`、`ip`，分别构造来源地址头和 RemoteAddr | 按 `X-From-IP`、`X-Real-IP`、`X-Forwarded-For` 首值、RemoteAddr 的顺序匹配；前项未命中时继续后项 | 未执行 |
| AZ-08 | URL 配置 `az`、`ip`，再分别用 `-Dlbd.az`、`-Dlbd.ip` 覆盖；另测系统属性为空 | 非空系统属性覆盖 URL；空系统属性清除对应 URL 配置，按剩余参数或自动识别路径处理 | 未执行 |
| AZ-09 | 模拟 driver 本机 IP 自动解析失败，随后恢复 config-server 连通性 | 当次不发送自动解析 IP，由服务端按来源 IP 兜底；按 `azRefreshIntervalSeconds` 退避重试，恢复后可解析并缓存 IP | 未执行 |
| AZ-10 | 匹配 az2，但 az2 未配置代理；保留其他合法 AZ 映射与默认集合 | 下发默认集合和 `policy=default`，不下发空列表 | 未执行 |
| AZ-11 | 省略 schema 的 `proxy`，仅配置合法 `az.proxy`；分别请求亲和集合和 `policy=default` | 亲和请求返回本 AZ 集合；默认请求返回所有 AZ 代理的去重并集 | 未执行 |

## 故障兜底与恢复回切

| 编号 | 用例与操作 | 预期结果 | 测试结果 |
| --- | --- | --- | --- |
| AZ-12 | az2 正常使用 P2 时停止 P2，P1、P3 保持正常，持续执行 SQL | P2 判为不可达后进入 AZ fallback，异步以 `policy=default` 拉取默认集合；加入 P1、P3，可用兜底代理承接新连接，业务在可能的短暂异常后恢复 | 未执行 |
| AZ-13 | 在 AZ-12 的故障状态持续观察至连接池稳定 | P2 保留用于恢复探测但无可用连接；P1、P3 持有连接并逐步均衡，总连接数收敛到目标值；周期不可达告警不造成重复进入 fallback | 未执行 |
| AZ-14 | 将 az2 配为 `[P2, P2b]`，只停止 P2 | 本 AZ 尚有 P2b 可达，不进入跨 AZ 兜底；新连接由 P2b 承接，故障节点持续被探测 | 未执行 |
| AZ-15 | 将 az2 配为 `[P2, P2b]`，停止两个代理，再只恢复其中一个 | 全部不可达时进入兜底；本 AZ 已有可达节点且满足恢复检查条件后回切，无需等待全部节点恢复 | 未执行 |
| AZ-16 | 在 AZ-12 降级稳定后恢复 P2 | 连续健康检查达到 `recoverCheckCount` 后退出 fallback；P1、P3 停用并摘除，P2 接回新连接且逐步补齐；分别记录回切时连接最低值和 SQL 耗时、异常 | 未执行 |
| AZ-17 | P2 恢复不足规定的连续健康检查次数后再次故障，随后稳定恢复 | 不提前退出 fallback；无可达本 AZ 节点时恢复计数重置，稳定恢复并重新满足条件后才回切 | 未执行 |
| AZ-18 | 配置 `recoverCheckCount=1` 和大于 2 的值分别执行恢复测试，期间产生业务连接失败回调 | 回切由实际连续健康检查次数决定；业务失败回调不增加或清空连续健康检查恢复计数 | 未执行 |
| AZ-19 | 首次故障进入兜底前使 config-server 不可用，保持其他代理正常；随后先恢复 P2，再恢复 config-server | 兜底请求失败不清空已有集合，不反复排队提交相同降级任务；无兜底缓存时不保证跨 AZ 可用；P2 恢复后可退出降级，未取得有效兜底集合时恢复检查次数上限为 2 | 未执行 |
| AZ-20 | 完成一次降级和恢复后再次停止 P2，默认集合内容保持不变 | 能再次加入缓存中的兜底节点；即使默认请求返回业务码 304，也不会因集合相同而遗漏状态切换 | 未执行 |
| AZ-21 | 分别用进程挂起、网络丢包 100%、连接黑洞模拟 P2 故障，再恢复 | 按健康检查及 JDBC 超时识别故障并兜底，无无限等待；恢复后满足检查条件即可回切，记录不同故障的实际恢复耗时 | 未执行 |
| AZ-22 | P2 故障并已兜底后，再停止 P1、P3，随后逐个恢复 | 无可用代理时请求明确失败或超时，不报告成功；兜底代理恢复后业务可恢复，P2 恢复后可回切 | 未执行 |
| AZ-23 | 业务进程启动前停止本 AZ 全部代理，保持 config-server 和默认集合中其他代理正常 | 启动阶段可触发默认集合兜底并建立可用连接；无永久卡死，记录启动是否成功及耗时，之后本 AZ 恢复可自动回切 | 未执行 |
| AZ-24 | 故障与回切期间持续执行读写和事务 | 记录成功率及延时；失败事务不得被误报提交成功，不假定跨连接自动重试或事务迁移；恢复后连接可继续使用，核对提交与回滚后的数据 | 未执行 |

| --- | --- | --- | --- |
| AZ-25 | 正常运行中将 `proxy.policy` 从 `default` 改为 `az`，再改回 `default` | 无需重启即可按刷新周期切换；开启后收敛到本 AZ，关闭后恢复默认集合并停止 AZ 降级状态管理 | 未执行 |
| AZ-26 | 正常状态在本 AZ 增加 P2b，再移除 P2，保留健康 P2b | 新代理加入并逐步均衡，旧代理摘除；有可用本 AZ 节点时不进入 fallback | 未执行 |
| AZ-27 | 降级期间更新默认集合，增加健康 P4 并移除 P1，保留健康 P3 | 默认集合按刷新周期更新，P4 加入、P1 摘除；故障本 AZ 节点继续被探测 | 未执行 |
| AZ-28 | 降级期间更新本 AZ 映射，加入健康 P2b | 按 `azRefreshIntervalSeconds` 拉取新本 AZ 集合，探测并满足恢复条件后回切到更新后的集合 | 未执行 |
| AZ-29 | 运行中调整网段映射，使业务节点从 az2 归入 az1，避免配置网段重叠 | 下一轮有效配置刷新后返回新的 AZ 集合，客户端收敛到 P1，旧集合不再接收新连接 | 未执行 |
| AZ-30 | 分别请求亲和集合和默认集合，携带各自上次的 `md5`，重复轮询并切换策略 | 相同变体未变化时返回业务码 304；两个变体的摘要独立维护，不会因缓存串用保持错误集合 | 未执行 |
| AZ-31 | 将默认集合设置为与 az2 集合相同，切换 `default/az`；另携带 az1 请求的摘要发起 az2 请求 | 地址列表相同而策略变化时仍返回新响应，客户端更新能力状态；跨 AZ 使用旧摘要不会错误返回 304 | 未执行 |
| AZ-32 | 配置全局 `az.list`，schema 不配；再给该 schema 配置不同的合法 `az.list` | schema 缺省时使用全局配置；配置 schema 级列表后以其为准，其他 schema 不受影响；etcd、nacos、local 分别验证 | 未执行 |
| AZ-33 | 分别提交跨 AZ 网段重叠、代理重复归属、未知 AZ 映射，以及 AZ 策略缺少必要列表的配置 | config-server 拒绝非法配置并记录错误；运行中保留上次有效配置；首次启动无有效配置时明确失败，避免静默生效 | 未执行 |

## 结果记录要求

* 执行后再填写「通过 / 失败」，未执行项保持原状态；失败项记录复现步骤、配置、客户端版本、相关日志和实际结果。
* `sql-proxy-count` 包含池中保留用于探测的节点，不能直接视为可承接请求的代理数；结合 `online`、`reachable`、`usable` 与连接数判断。
* 降级期间故障本 AZ 节点可以保持 `online=true`，但 `reachable=false`；回切时兜底代理即使仍可达，也应停止接收新连接并在连接释放后摘除。
* 后台连接逐步补齐不等于业务持续中断；反之，最终连接池正常也不证明切换期间无损。以持续 SQL 请求与事务数据校验结果作为业务验收依据。
