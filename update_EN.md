
# 1.1.0-SNAPSHOT (2026/10/15)
### Added
* Multi-AZ awareness for remote mode: new URL parameters `az` (local availability zone, optional; leaving it unset means config-server auto-detects the zone from the reported `ip`, which is the normal usage), `ip` (local IP, optional, overrides the auto-resolved value), `azRefreshIntervalSeconds` (default 30s) and `recoverCheckCount` (default 2)
* The driver always reports the local `ip` (an explicit configuration wins; otherwise it is resolved once from the local address of the socket connected to config-server and cached; if resolution fails the parameter is skipped for that request, config-server falls back to the request source IP, and the resolution is retried after backing off for `azRefreshIntervalSeconds`). Reporting `ip` is not tied to whether `az` is configured: an unset `az` is exactly the auto-detection case, where inferring the zone from the request source IP is unreliable behind nginx/NLB
* The driver always sends the client feature level `clientFeatureLevel` (currently `2`) and `clientVersion` (for config-server log observation only) when calling config-server. The level is a monotonically increasing integer compared as an integer by config-server, which avoids fragile version string comparison; a `ClientFeatureLevel` enum maps the level to a readable name for logs (`1` -> `legacy`, `2` -> `az-fallback`)
* Support for the new `policy` field in the config-server response (the policy actually applied to this response): `az` when a zone is matched, `default` otherwise. The driver treats any non-empty `policy` other than `default` as an affinity declaration and enables the fallback capability accordingly, so no degraded behavior and no noisy logs are produced while config-server does not enable AZ (it returns `default` or omits the field), and driver needs no change when new policies are added; a `304` response reuses the list and `policy` of the previous response of the same variant
* Automatic degradation when the whole local-zone set becomes unreachable: the driver immediately requests the default (fallback) set once with `policy=default` and uses it for new connections. Degradation is edge-triggered (state bit), so hot paths such as `syncCreating` never fire duplicate fallback requests, and at runtime that fallback pull runs on the refresh thread so the triggering thread is never delayed by config-server connect/read timeouts. That asynchronous pull is de-duplicated to a single in-flight request: until the fallback set takes effect, AZ reachability flapping produces repeated degradation edges, and without de-duplication those pulls would queue up on the single refresh thread, each holding the lock until it times out
* `SqlProxyProvider.onReachabilityCheck` gains a `startup` parameter that puts the "startup round may block, runtime round must not" constraint into the SPI contract: with `startup=true` (called by the startup thread) the provider may settle synchronously, and startup success depends on whether a node is usable when the callback returns; with `startup=false` the callback may run on a business thread (`getConnection` -> `syncCreating`) and the provider must settle asynchronously and publish on a later round
* The driver switches back to the local zone once a local-zone node passes `recoverCheckCount` consecutive health checks. While the fallback set has not taken effect yet (the pull failed, or the server has no default set) there is nothing to switch to, so the hysteresis is capped at 2 checks: enough to absorb single-round AZ flapping without holding the degraded state after the zone genuinely recovers. Single-layer deployments behave exactly as before
* The driver only maintains the set it currently needs: the local-zone set alone when healthy, and the fallback set plus the local-zone set while degraded (the local-zone set stays in the pool and keeps being probed, since recovery is decided from the reachability snapshot of pooled nodes). After switching back, the fallback set is **removed from the pool** instead of lingering as dormant nodes with dormant connections (those connections are neither balanced nor ever reclaimed); the cost is re-probing and re-connecting when the next failure adds them back, which is acceptable because failures are rare
* While degraded, the fallback set is refreshed every 5s and the local-zone set every `azRefreshIntervalSeconds`; the two request variants maintain independent `md5` values. After recovery the fallback set is no longer in the pool and is only refreshed slowly every `azRefreshIntervalSeconds` to keep the cache warm for the next degradation (an empty list is treated as a faulty response and skipped rather than clearing the fallback set)
* When a pool leaves load balancing (marked as not taking part in balancing, marked unreachable, or added in an unusable state) its idle connections are reclaimed right away and a connection still in use is closed when it is returned; `close` runs outside the lock because closing a bad connection may block. Such a pool is no longer in the borrow queue or the balance queue, so a stranded idle connection is never reclaimed by any path and only inflates `totalCount`: `rebalance` then wrongly concludes that physical connections are in surplus and starts reclaiming idle connections from the active pools, which shows up as fallback nodes connecting and disconnecting in a loop
* Startup path adapted: if no local-zone node is reachable during initialization, the driver enters the degradation flow directly (the startup round pulls the fallback set synchronously before deciding; when both sets are unusable it still throws the existing `There is no reachable sql proxy`)
* All AZ logic is confined to `RemoteSqlProxyProvider`: `ConnectionManager` only knows about "node sets" and "whether a node takes part in load balancing", via a new `setUsable` callback and a per-round reachability snapshot; the connection pool, balancing and selection paths carry no AZ concepts. `SqlProxyStats` gains a `usable` field (when `online`/`reachable` are both `true` but the node gets no traffic, this tells you it is in the pool without taking part in balancing) and the stats log prints it
* Stricter URL validation: a `url` containing a newline, carriage return or tab is rejected instead of being parsed. The `url` and its parameters are both sent as request parameters and printed to the log, where control characters can forge a separate log line; a jdbc url is meant to be a single line, so control characters always indicate a configuration error
* Only remote mode is affected; `local` mode and `lb-driver-druid` are unchanged
* `az` and `ip` can also be overridden by the system properties `-Dlbd.az` / `-Dlbd.ip`, which take precedence over the same parameters in the URL: both describe the deployment environment and one URL is often shared by a batch of machines (container images, shared configuration), so only `-D` can override them per machine. An empty value means "not configured" (useful to clear a value inherited from a shared URL on a single machine). Like the URL parameters, values containing control characters are rejected so that no fake log line can be forged
> Zone definitions (`az.list`), the zone-to-sql-proxy mapping (`az.proxy`) and the delivery policy (`proxy.policy`) belong to the config-server side; see the next section.

### config-server: multi-AZ delivery
* Three new optional fields: `proxy.policy` (`default` / `az`, defaults to `default`), `az.list` (zone name plus its networks; a zone supports multiple networks, IPv4 only) and `az.proxy` (zone-to-sql-proxy-node-list mapping). Legacy configuration (`proxy` only) is fully compatible; leaving them unset behaves exactly as before multi-AZ was introduced
* `az.list` can be configured globally in the `application.yml` of config-server (supported by all three data sources `etcd`/`nacos`/`local`, all read from `lb-driver-config-server.config`). When configured globally it can be omitted in each schema; a schema-level value wins
* When `proxy` is omitted in a schema, the default (fallback) list is the union of all nodes in `az.proxy`
* New optional parameters of `/fetch_sql_proxy_list`: `az`, `ip`, `policy`, `clientFeatureLevel` and `clientVersion`. AZ matching priority: an explicit `policy=default` in the request -> `az` in the request (must exist in the effective `az.list`) -> `ip` in the request -> source IP of the request (`X-From-IP`, `X-Real-IP`, first value of `X-Forwarded-For`, `RemoteAddr`) -> default list. The default list is also delivered when no zone matches, the matched zone has no node, or the client feature level is too low. The candidate order puts `X-From-IP` / `X-Real-IP`, which the access layer overwrites and a client cannot forge, before `X-Forwarded-For`, which a caller can craft freely; it only infers the zone (a performance optimization) and is not a security boundary, authorization is still enforced by apiKey
* The response contains a new `policy` field (the policy actually used). The digest covers `policy` and the matched zone, so different zones and different policies naturally produce different `md5` values and a shared `md5` can never make a client keep a stale policy after a `304`. The server no longer keeps an `md5` cache: it compares the digest computed for the current request (with the old implementation a freshly changed configuration could answer a stale `304`), which also removes the cache eviction problem
* For `/fetch_sql_proxy_list`, an `Authorization` header without the `Bearer ` prefix is rejected as `403` (previously `substring` threw an out-of-bounds exception and turned it into a `500`, which would be taken as a server fault and trigger alerts)
* Capability gate: only clients that send `clientFeatureLevel >= 2` receive an AZ list. An older driver (which does not send the parameter and is treated as 1) still receives the default list, so it never silently loses the cross-zone fallback capability
* Validation rules (an invalid configuration makes the schema fail to load/update and keeps the previous configuration): an illegal `proxy.policy` is rejected; keys of `az.proxy` must exist in the effective `az.list`; the same node must not belong to multiple zones; networks of different zones must not overlap; when `proxy.policy=az` neither the effective `az.list` nor `az.proxy` may be empty; `az.proxy` is still accepted while `proxy.policy` is `default` (with a warning that it does not take effect), so the configuration can be staged before the policy is switched
* Node reachability probing is now deduplicated and concurrent: the default list and all zone nodes are merged and deduplicated so each node is probed once, and `/monitor` no longer performs 2 x N serial 1s connections, so loading and monitoring no longer slow down linearly with the node count
* The probe pool now uses a bounded queue with `CallerRunsPolicy`: when the pool is saturated the submitting thread runs the probe itself, which keeps concurrency without letting tasks pile up in the queue until they time out and get misreported as unreachable (the policy never triggers with an unbounded queue). Nodes not collected within the wait budget are logged as "result unknown" rather than `not reachable`
* `/monitor` reports `policy` and `azSize` in `schemaInfo` and a new `azProxyDetail` array with the reachability of each zone node; `reachable` is `1` for reachable, `0` for definitely unreachable and `-1` when the probe did not finish within the wait budget (result unknown, do not treat it as unreachable)
* New unit tests cover configuration parsing and validation, the AZ matching priority and the response digest (36 cases in the `lb-driver-config-server` module)

# 1.0.1 (2026/08/13)
### Added
* Default the config-server port to 80 when it is omitted from the remote URL

### Fixed
* Fixed logical connections allowing subsequent operations after fatal SQL exceptions on the underlying physical connection
* Fixed connection close cleanup to always unregister logical connections and prevent unhealthy physical connections from returning to the pool
* Implemented `isValid()` (previously a stub that always returned false) so connection pools can validate logical connections correctly: closed or broken connections return false, idle connections return true, and held connections delegate to the underlying physical connection's `isValid()`
* Hardened the fatal-error path: mark the logical connection broken before releasing the physical connection to avoid a transient misjudgment by concurrent `isValid()`; made `realConnection` volatile; close-Statement exceptions no longer mask the original fatal exception
* `isClosed()` now returns true when the connection is closed or broken by a fatal error (previously a broken connection still returned false, inconsistent with its unusable state)

> See [doc/fatal_error.md](doc/fatal_error.md) for details on the fatal-error handling changes, compatibility with connection pools (Druid / HikariCP / DBCP / c3p0 / tomcat-jdbc), and version recommendations.

### Security
* Restricted `/health/online` and `/health/offline` to loopback addresses by default; set `-DconfigServerOnlineOfflineLoopbackOnly=false` to disable the restriction
